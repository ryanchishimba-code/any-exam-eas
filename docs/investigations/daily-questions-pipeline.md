# Daily questions pipeline

The shared pack described below is now implemented on this branch: 20 questions per practice field per Chicago date, a separate Review misses sitting, and the two serve bugs fixed. `/daily` is unchanged. The tables under this note describe the behavior that implementation replaced. No production data was read or written.

There is no single daily-question pipeline. Three mechanisms are live, and a fourth study-plan API exists beside them. None of them is a global, bank-backed pack of about 20 questions.

| Surface | What a student gets | Source | Clock | Same for every student? |
| --- | --- | --- | --- | --- |
| Public Question of the Day (`/daily`) | 1 question | 7 hard-coded items per exam | America/Chicago | Yes |
| Dashboard “Today’s set” (`daily_set`) | 25 by default, often a mix of misses and new items | Question bank | Student timezone, else Chicago | No |
| Question-bank style “Today” and readiness “Today” link | 20, 40, or 60 | Question bank, mastery engine | Not a calendar rotation | No |
| Learning-hub daily assignment | A plan of links, not a fixed question set | Hard-coded modules | UTC date | The module rotates globally; weak-topic links are personal |

No cron generates, rotates, or emails a daily question set. `vercel.json` schedules keepalive, question-bank sync, billing reminders, analytics, and social publish. Sync refreshes published inventory counts. It does not pick daily questions.

## Direct answers

**Is the daily set generated by AI, picked from the bank, or hard-coded?**

Both of the student-facing question sets that exist today are one or the other, and neither is generated at serve time.

- Public Question of the Day is hard-coded in `src/lib/demo/qotd.ts`. Serve time does not call a model and does not read `QuestionBankItem`.
- The signed-in daily set and the older mastery “Today” set are picked from `QuestionBankItem`. Bank rows may have been written earlier by generation scripts (`generationVersion` on the row). The request path does not generate stems, options, or keys.

**How many questions per exam, and how often do they rotate?**

- Public pages: 1 question per exam per Chicago day, chosen from a pack of 7. The same item returns every 7 days (`dayIndex % 7`).
- Signed-in daily set: 25 (`TODAY_SET_DEFAULT_SIZE` in `src/lib/learning/today-set.ts`). A new composition is chosen once per student, per field, per local calendar day, then stored. It does not rotate on a shared schedule.
- Mastery “Today”: 40 unless the URL asks for 20 or 60 (`resolveTodaySize`). It is rebuilt from the student’s skill cells whenever it is started. It does not rotate by calendar day.
- The learning-hub plan rotates its featured module with a UTC day index. NCLEX and NAPLEX plans in that file are static link lists. The panel component is not mounted anywhere.

**Do they rotate per day globally or per user?**

- Question of the Day rotates globally, one Chicago calendar.
- The signed-in daily set is per user. The seed is `userId|fieldId|YYYY-MM-DD` in the student’s timezone (`todaySetRandom` in `src/lib/learning/today-set.ts`). Two students on the same board on the same civil day get different questions.
- Mastery “Today” is per user and is not pinned to a date. Starting it twice with unchanged skill cells returns the same ids because the sort is stable. Answering changes the next set immediately.

**Do the picks respect `active = true` and `qaPassed = true`?**

Selection queries do. The signed-in reload path does not fully honor `active = false`.

- New daily-set candidates and the mastery candidate query both require `active: true` and `qaPassed: true`.
- Review ids are passed through `loadServableReviewBankIds`, which uses the same two flags, then `ineligibleServedIds`.
- `loadBankItemsByIds` (`src/lib/full-exam/load-bank-items-by-ids.ts`) reloads a stored daily set with `isStudentEligible`. That check treats `qaPassed === false` as ineligible. It treats `active === false` as ineligible only when `active` is present on the object. `enrichBankItemFromRow` in `src/lib/mpje/parse-bank-options.ts` accepts `row.active` and never copies it onto the `BankItem`. A stored id whose row is later set `active = false` still loads and is still served for the rest of that local day.
- Public Question of the Day never reads those columns.

**Is there per-exam isolation?**

The signed-in daily set and the public packs are isolated by field. The mastery “Today” entry points are not, for PANCE, AANP FNP, and NPTE-PT.

- Daily-set queries use `reviewFieldIdsForQuery`. Aliases stay inside one board (`nclex` → `nursing`, `naplex` → `pharmacy`). `mpje` is excluded so pharmacy-law rows are not pulled into PANCE. After the query, `bankRowMatchesPracticeField` drops a row whose canonical field does not match, including Step 3 rows stored on `usmle-step-2` when the student is on Step 2, and the reverse.
- Each Question of the Day pack is keyed by exam slug. A page never renders another board’s item.
- Question-bank style `today` remaps every field that is not pharmacy and not USMLE onto the NCLEX mastery builder (`StudyBankPractice.tsx`). Readiness links every exam, including PANCE, AANP FNP, and NPTE-PT, to `style=today&count=20`.

**Do repeats happen?**

Yes, on every surface.

- Question of the Day repeats every 7 days, for every visitor. Dated URLs that share the same index modulo 7 are the same item. Historical URLs back to 2024-01-01 stay valid.
- On the signed-in daily set, ids inside one set are deduped. Answered bank ids are excluded from the “new” pool via `QuestionAttempt`. Unanswered ids from earlier days are only soft-avoided, and only for the 14 snapshots kept on `UserPreference.metadata` (`TODAY_SET_HISTORY_CAP`). Day 15 can select them again. Misses and due spaced-review items are meant to return; a short miss list is repeated every day because the picker falls back to avoided ids when the due pool is small.
- Mastery “Today” has no seen-id window. The same high-weight unseen or shaky items lead the set until the skill cell moves.

**What breaks when an exam has few eligible questions?**

- Signed-in daily set: the set gets shorter. It does not borrow another board, and it does not generate fillers. Zero servable ids return HTTP 404 `EMPTY_DAILY_SET`. The dashboard copy is “No questions ready for this board yet.”
- If the student still has servable misses, those fill the empty new-item slots, so a thin bank becomes a review loop of the same misses.
- Mastery “Today” also returns a shorter set, capped by whichever rows the unordered `take: 2500` query happened to return. An empty candidate list is HTTP 404 `EMPTY_TODAY`.
- Question of the Day does not consult the bank, so a thin or empty bank does not change the public page. The public page also cannot grow when the bank is large.

**What is broken today?**

Confirmed from the code paths below:

1. Retired rows with `active = false` stay in a daily set that was already chosen, until the student’s local midnight.
2. PANCE, AANP FNP, and NPTE-PT can be served NCLEX items when the student starts mastery “Today” (question-bank style, or the readiness link).
3. Nothing serves a shared, deterministic pack of about 20 bank questions. The public feature is 1 of 7 hard-coded items. The signed-in feature is a personal 25-item mix.
4. Answer-key balance is not implemented on any bank-backed set. Topic spread on the daily set is only as good as the random id windows that were loaded.
5. A retirement mid-day shrinks the stored set when the row fails a check the loader can see (`qaPassed`, structural eligibility, `curationMeta` retirement). The holes are not refilled until the next local day.

Not confirmed, because this run did not query production: whether any board’s eligible pool is under 20, whether legacy Step 3 rows still sit on `usmle-step-2`, and whether any stored snapshot is currently serving an inactive id. The code paths that would do those things are live.

### 1. Public Question of the Day

Files:

- Pack and selector: `src/lib/demo/qotd.ts` (`QOTD_BY_EXAM`, `getQotdForExam`)
- Date helpers safe for the client: `src/lib/demo/qotd-public.ts`
- Answer reveal (key stays off the first paint): `src/lib/demo/qotd-reveal.ts`
- UI: `src/components/marketing/QotdPractice.tsx`, hub inbox `src/components/marketing/DailyInboxCapture.tsx`
- Pages: `src/app/(marketing)/(with-flagship)/daily/page.tsx`, `daily/[exam]/page.tsx`, `daily/[exam]/[date]/page.tsx`, `daily/[exam]/[date]/opengraph-image/route.tsx`
- Sitemap: `src/app/sitemap.ts` (undated exam URL plus today’s dated URL only)
- Subscribe endpoint: `src/app/api/daily/subscribe/route.ts` writes one analytics event (`daily_question_subscribe`). It does not store a mailing list table and it does not send a question.

Selection is `pack[dayIndex % pack.length]`. `dayIndex` is days since 2024-01-01. `parseQotdDate` rejects malformed dates, dates before that epoch, and any Chicago date after today, and the dated page 404s. Future URLs call `connection()` before `notFound()` so a tomorrow URL is not cached as a permanent 404.

Each item is hand-written: stem, four options, a correct index, and a one-sentence rationale. Ids look like `nclex-01`. They are not bank ids. The correct index cycles `1, 2, 3, 0, 1, 2, 3` in every pack, so the seven-day loop is balanced across A–D, and a single day is only one letter.

Caching and SEO:

- `/daily` and `/daily/[exam]` use `revalidate = 60` and are prerendered from the Chicago date. The item changes within about a minute of midnight Central, without a deploy.
- Dated pages prerender today and use `revalidate = 86400` for other allowed dates.
- The answer key lives in `qotd.ts`, which is not imported by client components. The browser receives `toPublicQotd` (stem and options only) until reveal.
- These pages do not touch the database. Core Web Vitals for `/daily` are independent of bank size.

The hub’s featured board is `EXAM_SLUGS[dayIndex % 6]`, so the featured exam also rotates daily, separately from which item each exam shows.

### 2. Signed-in daily set (the dashboard “Today’s set”)

This is the set the dashboard actually starts.

Files:

- Composer: `src/lib/learning/today-set.ts`
- Loader: `src/lib/learning/today-set-plan.ts` (`selectTodaySet`, `loadServedTodaySet`, `loadTodaySetPreview`)
- Snapshot storage: `src/lib/learning/today-set-preference.ts`
- Browser handoff (2 minutes, `sessionStorage`): `src/lib/learning/today-set-stash.ts`
- APIs: `src/app/api/study/daily-set/route.ts` (POST), `src/app/api/study/daily-set/preview/route.ts` (GET, `Cache-Control: private, no-store`)
- UI: `src/components/dashboard/DashboardTodayBlock.tsx`, `TodaySession.tsx`, `StartTodaySetButton.tsx`
- Player: `src/components/study/StudyBankPractice.tsx` when `style=daily_set` (stash first, otherwise POST)

There is no `DailyQuestion` table. The chosen ids are stored on `UserPreference.metadata` under `todaySets.v1.boards[fieldId].days`, capped at 14 days and 120 ids per list. Habit streaks live beside that in `dailyHabit`, keyed by exam slug, capped at 120 days. Redis/L1 cache key is `today-set-served-v2:{userId}:{fieldId}:{day}:{size}`, with TTL until the next midnight in the study timezone (`cacheGetOrSetDeduped`). `invalidateTodayServedCache` only deletes keys already in that process’s memory; other instances keep the cached ids until midnight. The comment in `today-set-plan.ts` says the account snapshot is the source of truth.

Size:

- `resolveTodaySetSize()` with no goals returns 25. The POST route calls it with no goals, so a saved daily goal, week goal, or exam-date plan does not change this set.
- POST then clamps to the usage allowance. Paid and trial `dailyQuestions` are `null` (unlimited) in `src/lib/study/usage-limits-config.ts`. A trial lifetime cap can still shorten a sitting.
- Review is capped at 60% (`TODAY_REVIEW_MAX_SHARE`). A full set of 25 is at most 15 review and at least 10 new, until the new pool runs out. Leftover review backfills a short new pool.

How a set is built (`selectTodaySet`):

1. Open misses from `loadStillIncorrectBankItemIds` (same queue as Review incorrect, limit 300), then due `QuestionMastery` rows (`nextDue <= now`, limit 300), filtered to servable bank ids.
2. Seen `QuestionAttempt.bankItemId` values are a hard exclusion from the new pool.
3. Ids from the previous 14 stored days are a soft exclusion for new items and an avoid-list for review.
4. New rows are `QuestionBankItem` with `active: true`, `qaPassed: true`, and `fieldId` in the alias set. `ineligibleServedIds` removes rows the structural serve rule rejects (broken SATA, incomplete cases, `curationMeta.itemQa.retiredAt` / `retiredReason`, and the other checks in `STUDENT_ELIGIBLE_SQL`).
5. The loader does not scan the whole bank when it is large. It counts, then reads up to 8 random id windows (`orderBy: id`, page size at least 40, at most 500). If that is still short of the slots needed, it walks the table. Windows exist because consecutive ids cluster by topic.
6. `composeTodaySet` places open misses, then spaced review, then weighted new items. New items are spread across topic keys when the sampled pool has two or more topics. Weights come from the exam blueprint (`weightForRow`). A row that matches no category gets weight `0.001` and can still be drawn. Nothing in this path balances the correct-option index.
7. The random source is a seeded hash of user, field, and calendar date, so the same inputs and the same database state produce the same ids.

Stability and retirement:

- The first successful build is written to `UserPreference`. Later requests that day reuse it, including after the student answers, so the set does not reshuffle mid-sitting.
- On every serve, `loadBankItemsByIds` reloads the ids and `recountTodayMix` drops ids that fail to load or fail `isStudentEligible`.
- `qaPassed: false`, a structural defect, or `itemQa.retiredAt` while `active` is still true will drop the id. The set becomes shorter for the rest of the day. The snapshot is not rebuilt to fill the hole.
- `active: false` does not drop the id, because `active` is discarded in `enrichBankItemFromRow` before eligibility runs. That is the inactive-item hole.
- The calendar day is the browser timezone sent by the dashboard (`browserStudyTimeZone`). A missing or invalid zone falls back to America/Chicago. The question-bank fallback POST (`StudyBankPractice`, stash miss) does not send `timeZone`, so a student outside Chicago who misses the stash near midnight can be assigned a second set under the Chicago date.

Player payload: `shuffleOptions: false`, correct answer withheld until submit (`withholdPreSubmitExamQuestion`). The letter the student sees is the option order stored on the row.

### Database columns that matter

`QuestionBankItem` (`prisma/schema.prisma`):

- `fieldId` — board isolation
- `active` — default `true`
- `qaPassed` — default `false`; comment says only passed rows are served in practice
- `stepLevel` — USMLE step separation
- `subjectId`, `topicCategory`, `blueprintDomain`, `blueprintTopic` — topic spread
- `curationMeta.itemQa.retiredAt` / `retiredReason` — retired while `active` may still be true; the structural SQL excludes these
- `correctAnswer`, `options` — would be the inputs for answer-key balance; unused for that today

Related tables: `QuestionAttempt` (seen ids and the miss queue), `QuestionMastery` (spaced due), `UserPreference.metadata` (the 14-day snapshot and the streak). No column stores “this id is the daily question for this date.”

### What a small bank does, in code

`composeTodaySet` never pads to the requested size. `todayUnseenNeeded` asks only for the slots the review cap left open. `collectUnseenCandidates` returns whatever eligible rows it found. The API treats `mix.ids.length === 0` as empty and any positive shorter length as a successful shorter set. Preview shows `empty: true` only when the mix line is null.

A board with 1–19 eligible new items and no misses gets a set of that length, then repeats those items once the 14-day soft window expires, or sooner if they were answered and are due again as review. A board with zero eligible rows and zero servable misses shows the empty state. Neither path crosses `fieldId`.

## Problems that matter for a 20-question pack

1. **Inactive rows can be served after retirement.** Selection is gated. The all-day snapshot is reloaded through a mapper that drops `active`. `qaPassed: false` is caught; `active: false` is not. Redis can keep the id list until local midnight on every instance.
2. **Mid-cycle retirement shrinks the set and does not replace the slot.** Students can finish a day under the target with no explanation other than a shorter mix line.
3. **The set is personal, not a daily pack.** Repeats, topic mix, and which items appear depend on that student’s misses, due reviews, attempt history, and timezone. Two students do not share “today’s questions,” so the set cannot be reviewed once editorially as the day’s pack.
4. **Topic balance is a sample, not a schedule.** Eight id windows can miss whole blueprint categories on a large bank. Consecutive-id clustering is why the windows exist, and the windows do not guarantee a weighted spread.
5. **Answer keys are not balanced** on either bank-backed set. Option order is fixed (`shuffleOptions: false`), so a run of the same correct index is visible.
6. **Wrong-board serve on mastery “Today”** for PANCE, AANP FNP, and NPTE-PT, from the bank style picker and from readiness `todayHref`.
7. **USMLE public QOTD is one pack for three steps.** The signed-in set is per step. Those are different products wearing the same name.
8. **Public QOTD is outside the QA gate.** Retiring a bank row does not change `/daily`. The seven items can repeat forever, and their quality is whatever review the source file got. They are also the SEO surface: `/daily` is in the sitemap, cached for 60 seconds, and must not start reading the bank on the document request.
9. **Two clocks.** Public pages and the daily-set fallback use Chicago. The dashboard daily set uses the browser zone. The learning-hub index uses UTC. A student can see “today” roll at three different times.
10. **Mastery “Today” is an uncapped read.** Up to 2500 full-enough rows per start, unordered, with no day cache. That is the expensive path. The dashboard’s daily set is cheaper (id windows plus a 25-id reload) but still recomputes from misses and mastery on a cache miss.
11. **Goals are unused.** `resolveTodaySetSize` can honor a daily goal, and the route never passes one. The live size is 25, not 20.
12. **Case rows can be drawn one at a time.** The daily-set candidate query does not restrict `itemType` and does not keep a case group together. A single item from a complete case can appear without its siblings.

## Proposed design

A global pack of 20, computed from the rows the question bank already serves, cached until Chicago midnight, and served by the existing daily-set API. No model call, no new table, no cron, and no change to `/daily`.

### Contract

- One pack per practice field per America/Chicago date. USMLE Step 1, Step 2, and Step 3 are three fields, matching the bank. The public `/daily/usmle` page stays the single curated item.
- Size 20. If the eligible pool is smaller, the pack is the whole pool and the mix line shows the real count. If the pool is empty, the API returns the current empty state. No other field is consulted.
- Every id is eligible under the same predicate the inventory stamp already uses: `active = true`, `qaPassed = true`, `fieldId` in that field, not a Step 3 row on Step 2, and `STUDENT_ELIGIBLE_SQL` (`src/lib/inventory/active-inventory-stamp.ts`). That predicate already excludes `itemQa` retirements.
- The same date and the same eligible id list always produce the same 20 ids, for every student.
- No id repeats until the cycle has used the pool. With pool size `P`, the repeat-free window is `floor(P / 20)` days. A pool under 20 repeats the next day; that is the honest limit, and the empty-state copy should say how many were available.
- Topics follow blueprint weights. Correct-option indexes are spread across the 20.
- A row that loses eligibility after the pack was cached is removed on the next request and replaced from a deterministic overflow, so the day stays full when the pool allows it. The replacement is written back to the same cache entry so the next student sees the same patch.
- `/daily`, its Open Graph images, and the sitemap stay on the hard-coded pack. The 20-question feature stays on the authenticated API, which is already `no-store` on the preview and already fetched by the client after the dashboard shell. Document HTML and LCP do not gain a bank query.

### Why this shape

A stored rotation table or a nightly cron would also work, and both cost more operationally. The bank is already indexed on `(fieldId, active, qaPassed, id)`. One ordered id read per field per day, plus a 20-row hydrate at serve, is the whole data path. The existing Redis helper (`cacheGetOrSetDeduped`) holds the result until Chicago midnight. The 05:00 UTC sync cron is the wrong clock for Chicago (it matches midnight only during daylight time) and is not required.

Keeping the personal miss-queue inside these 20 would make the pack differ per student, which is the behavior being replaced. Review incorrect and spaced review already have their own launches. The daily pack should be the rotating bank, and those modes should keep the misses.

### Selection algorithm

Run once per field per Chicago date. Cache the resulting id list.

1. Read eligible ids with `subjectId`, `blueprintDomain`, `topicCategory`, `correctAnswer`, and `options`. Order by `id`. Map each row to a blueprint category with the same helper the daily set uses now (`weightForRow` / `getExamBlueprint`). Map `correctAnswer` to an option index `0–3` when the item is a single-best-answer MCQ. Other item types go in an `other` key bucket so they still spread, without pretending they have a letter.
2. Inside each category, sort by id, bucket by answer key, and interleave the buckets. That stops a topic whose keys were all written as option B from filling the day with B.
3. Build one sequence by weighted round-robin across categories (largest remainder, then category id as the tie break). Walk that sequence in order. Day index `D` (days since 2024-01-01, same epoch as Question of the Day, Chicago date) owns the slice `D * 20` through `D * 20 + 20`, stopping at the end of the sequence. The last partial slice is a short day. The next day starts the sequence over. Do not wrap inside a day; wrapping is what would repeat an id inside the window.
4. Drop case-group item types from this pack (`case_study`, `unfolding_case`, `case_based`, and the CCS types the inventory already classifies as cases). A daily pack of standalone items avoids serving one case question without its siblings. NGN items that are standalone and already student-eligible can stay. This is a one-line filter on the pool, not a new scorer.
5. Cache key: `daily-pack:v1:{fieldId}:{chicagoDate}:{poolFingerprint}`. Fingerprint is the count of eligible ids plus the maximum `id` in that set, not `updatedAt`. A rationale edit on a still-eligible row does not reshuffle the day. A retirement changes the count or the max id only when the retired row was the max id; the serve-time check below covers the retirement that does not change the fingerprint.

### Retirement during the day

On each serve, reload the cached 20 with an explicit `where` of `id IN (...)`, `active: true`, `qaPassed: true`, and the field predicate. Do not trust `isStudentEligible` until `enrichBankItemFromRow` copies `active` (see the fix note below). Drop failures. For each hole, take the next id in that day’s sequence that is still eligible, not already in the pack, and not inside the current cycle’s earlier slices. Append the patch to the cached list. If the overflow is exhausted, serve the shorter pack.

A row retired in the morning is absent for every student who starts afterward. Students who already received the item in a sitting keep that sitting (the player stash and the in-progress session). The next start sees the patched pack. That is the same stability the current snapshot gives, without keeping a dead id.

### Where it plugs in

- `loadServedTodaySet` / `loadTodaySetPreview` call the pack selector instead of `selectTodaySet`.
- POST `/api/study/daily-set` keeps auth, field access, usage clamp, sealing, and `shuffleOptions: false`. Requested size becomes `min(20, allowance)`. The response shape (`questions`, `mixLine`, `playerHref`) stays, so `DashboardTodayBlock` and `StudyBankPractice` do not need a redesign. The readiness `todayHref` should be switched to `style=daily_set` when this ships, so PANCE, AANP FNP, and NPTE-PT stop opening NCLEX.

### Fix that has to land with the serve path

`enrichBankItemFromRow` must copy `row.active` onto the `BankItem`, or the daily-set loader must pass `active` into `eligibilityInputFromBankItem` itself. Until that is true, any code that reloads by id and then calls `isStudentEligible` will keep serving `active = false`. That fix changes every caller of the mapper, so it should ship only with this work and with tests that start from a row whose `active` is false.

### What this does to SEO and Core Web Vitals

- `/daily` remains static data, `revalidate = 60`, no database, no extra JavaScript.
- The dashboard already paints the shell and fetches the mix line afterward (`deferMix`). The pack read replaces that fetch’s query. It does not move onto the document.
- Cache the id list. Hydrate stems only for the 20 ids the player needs. Do not scan 2500 rows on the mastery path for this feature.
- Sitemap entries for `/daily` stay as they are. Do not add 20 question URLs per exam per day.

### Tests to write before it is turned on

- Same field, same date, same pool → identical ids, called twice.
- Different field → no shared ids, including a Step 3 row filed on Step 2.
- A pool of 50 yields 20, then a disjoint 20, then 10, then the first 20 again.
- A pool of 7 yields 7, and the next day is those same 7.
- A pool of 0 yields the empty code.
- Blueprint weights are reflected in a long sequence (a heavy category appears more often than a light one; not a snapshot of eight random windows).
- A 20-item slice is not all one option index when the pool has a mix of keys.
- Flipping `active` or `qaPassed` to false removes that id on the next serve and fills from overflow, and the second serve returns the patched list.
- `/daily/[exam]` still resolves with `getQotdForExam` and does not import the pack loader.

## Effort

This is one selector module, a cache key, a swap inside `loadServedTodaySet` / `loadTodaySetPreview`, the `active` copy on the bank mapper, a readiness link change, and unit tests around the selector. The dashboard and the player already speak the daily-set response.

It does not need a Prisma migration, a cron, a backfill, or a marketing-page rewrite. It should not be folded into a drive-by cleanup of mastery “Today”; that engine can stay dark for this pack and be removed in a later decision.

The risky part is product behavior, not code volume: students who currently receive their own misses inside “Today’s set” would receive the shared pack instead. Review incorrect remains available. That swap should wait for an explicit yes.

The `active` mapper fix is small and should ship in the same change as the pack, with a regression test. Shipping the mapper fix alone still changes who can be served on every path that uses `loadBankItemsByIds`, so it belongs in the approved change rather than in a silent patch.
